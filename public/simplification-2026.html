Platform Simplification · 2026 Action Plan · v1

From platform sprawl to one surface that scales for agents and customers.

Three schemas become one. Four services consolidate into bcore. Datomic gets cached and re-homed. New clients onboard in hours, not weeks. Documentation becomes agent-grade. Two tracks — Architecture owns the API surface; DevOps owns the runtime — working in rough priority order across four phases.
v1 · May 2026

Problem & Target

Today

Three GraphQL schemas (stable / incubating / experimental) make the API hard for humans and agents to reason about. AMS, Reporting, Indexer, and bcore live as separate services with overlapping logic. Datomic runs on PostgreSQL with no caching layer and oversized databases. Each realm gets its own k8s cluster. Onboarding a new client is a multi-week manual ramp. Errors are cryptic. Docs aren't built for retrieval.

Target

One unified schema with clear naming and self-descriptive errors. AMS, Reporting, and Indexer absorbed into bcore. Datomic on Cassandra with Memcache in front, smaller DBs, history offloaded to the warehouse. Single k8s cluster, namespace per realm, shared multi-realm services. Automated provisioning spins up a new client in hours. Agent-grade documentation feeds RAG cleanly.

Phase Flow

Phase 01
Standardize & Document
Naming conventions, error model, agent-grade docs, @fulltext deprecation finalized, migration approach standard. The foundation everything else builds on.
Phase 02
API Simplification
Three schemas collapse to one. Query complexity gate. Attributes history reverted. Functions templates leave the API.
Phase 03
Service Consolidation
AMS + Reporting + Indexer absorbed into bcore. Multi-realm shared services. Single cluster + namespace per realm. Datomic DBs shrunk.
Phase 04
Scale Infrastructure
Automated client provisioning. Memcache + Cassandra under Datomic. History to warehouse. Argo Workflows. Keycloak alternatives evaluated.

Two Tracks

ARCH · Architecture Track

Owns the API surface and service shape. Schema unification, naming, error model, service consolidation into bcore, documentation, query complexity. The track agents see.

DEVOPS · DevOps Track

Owns the runtime, data layer, and provisioning. Datomic re-platforming, Memcache, cluster topology, CI/CD migration, identity provider evaluation, automated client onboarding. The track customers feel at scale.

Outcomes by Phase

Phase 01

The contract is written. Naming, errors, and docs become predictable. Agents (ours and customers') can reason about the platform. CI lints the rules. Migration work has a standard playbook.

Phase 02

One API to integrate against. Three schemas become one. Heavy queries get blocked at the gate. Functions templates leave the API. The surface customers touch is dramatically smaller.

Phase 03

The platform stops being a constellation. bcore swallows AMS, Reporting, and Indexer's schema. Multi-realm services exist. One cluster, namespace per realm. Datomic gets right-sized.

Phase 04

Scale becomes a sales lever. A new client lands in hours. Datomic on Cassandra removes the PG ceiling. Memcache absorbs read spikes. CI/CD and identity are evaluated honestly, not by inertia.

Guiding Principles

Non-negotiables
  • One mental model per surface — if a customer or agent has to branch on "which schema / which service / which cluster", we haven't simplified yet.
  • Errors are a feature, not a leftover — structured, actionable, surfaced.
  • Documentation is built for retrieval, not for skimming — agent-grade or it doesn't ship.
  • Every migration has a rollback and a per-customer cutover plan.
  • Simplicity wins ties — if two designs are close, the one with fewer moving parts wins, even if the other is marginally faster.
  • Phases are sequential at the macro; in-phase work runs in parallel.
  • Priority is independent of phase — Critical in Phase 2 ships before Medium in Phase 1.
  • "Future" items get a decision, not a runway — we either commit or close them out, no permanent maybe.
