Gap Analysis · AI-Native SDLC Playbook × Release Pipeline v4

Your plan builds the last tier of the playbook first

Release Pipeline 2026 v4 is a strong release-operations plan. Measured against Anthropic's AI-Native SDLC Playbook it is missing a whole layer — the one the course treats as having no prerequisites at all. Below: where the two line up, the six foundation plays v4 omits, and thirteen initiatives drafted in your existing backlog format.

The finding

The playbook's dependency graph starts with six plays that have zero prerequisites: capture intent, CLAUDE.md, skills, feedback loop, hooks, plan mode. CI/CD sits in the fourth tier and closing the loop is last. Release Pipeline v4 contains none of the six — and its Phase 01 "Foundation" is made almost entirely of fourth- and final-tier work.

That is not a scoping error, it is a boundary choice: v4 is a release pipeline. Its own agent map begins at "Pickup," so everything upstream of a ticket — how intent becomes a spec, how a spec becomes a plan, how an engineer works with an agent — sits outside the plan. The consequence is that v4 spends its Phase 01 automating the coordination of a build process it never makes faster, and hard-codes human approval gates sized for today's throughput rather than tomorrow's.

The gate arithmetic

The playbook's central claim is that agents move the bottleneck: once build accelerates, review and approval become the constraint and have to be redesigned. v4's gate matrix was drawn for 2–4 releases a year while L-10 targets ten releases a day.

What to change

Your agent map assigns the Delivery Lead six approvals per release — scope, cut, notes, window, and two promotions — plus a rollback decision, and the CIE four more. At L-10's target cadence that is roughly a hundred human approvals a day concentrated on two roles. The releases will queue behind the calendar, and the phase-04 outcome ("closed loop") will be gated by a person's inbox.

Use the three-tier model you already have. L-01 defines Major / Minor / Hotfix by branch, scope, comms and testing. Extend it to define gate depth: a Minor auto-promotes to DEV and QA on agent sign-off with one human gate at PROD; a Hotfix carries smoke coverage and a single approver; a Major keeps the full chain unchanged. Then make it enforceable with hooks rather than policy — allow, block, or ask, decided by release tier and target environment. That keeps every SOC-scoped change inside the documented approver chain while removing the approvals that carry no judgment.

Recommendation · add a third track

v4 has two tracks: ENG builds and operates the release machinery, LEAD owns policy and customer comms. Neither one owns how viax writes software with agents — which is why the six foundation plays have nowhere to sit. Adding a third track is a non-destructive change: your four phases, initiative IDs and priorities all stay as they are.

DEVnew track
Development Track. Owns the agent-assisted development loop inside the repos — context, policy, verification, gates, and the artifact chain from intent to merged diff. Human-in-the-loop on agent outputs that shape design and code. Runs in parallel with ENG and LEAD inside each phase, on the same priority scale.

Revisions to existing initiatives

E-04add dependency
Testing agents that "update existing tests when code changes" is the exact failure mode the playbook warns about — an agent repairing the test instead of the code. Add D-01 and D-02 as dependencies so the verification command and the test-file protection hook exist before agents get write access to the suite. No change to scope or priority.
E-17supersede
Agent evals are currently Medium in Phase 04. But CLAUDE.md, skills and hooks are agent configuration, and E-04's testing agents and E-11's CI gates inherit whatever quality those have. Fold E-17 into D-09 and move it to Phase 02, High. Keep the named engineering owner per agent and the "agent on call" concept — those are good and the course has no equivalent.
E-14close the loop
Post-deploy correlation currently ends at "alerts route to the responsible team" — a human handoff, so the loop does not actually close. Have it emit an intent.md into the triage queue instead, carrying the anomaly, the evidence, the affected systems and the open questions, so a production signal enters the same pipeline as any other work. Add a versioned bands.yaml with tiered response: 1σ logs, 2σ diagnoses read-only, 3σ may open a PR or trigger a pre-approved runbook. Depends on D-05.
E-15re-sequence
Automated rollback recommendation is marked Future. Raise to High once D-12 lands — the recommendation engine is cheap and the rehearsed rollback is the expensive half. Human approval stays.
L-01extend
The three-tier model defines branch, scope, comms and testing per tier. Extend it to define gate depth per tier, and make the definition executable through D-03's hooks. This is the single highest-leverage edit in the plan: it is the mechanism that lets L-10's ten-releases-a-day target coexist with non-skippable SOC gates.
L-03reframe
Definition of Done currently requires a linked Jira release object. Define it as the artifact chain — intent → spec → plan → diff → review → incident record — with Git as the system of record and Jira as the reporting view over it. Same governance, fewer places for the truth to live.
SOCreframe
v4 proposes building "an immutable audit log per release." Most of that evidence set already exists once the artifact chain does: Git history gives author, timestamp, reviewer and diff; PR metadata gives the approver chain; the hook decision log gives every gate outcome; the OTel export gives the agent actions. Scope the custom build down to what those four cannot produce, and the SOC story gets stronger and cheaper at once.

Suggested order

Priority stays independent of phase, as in v4. This is only about what has to exist before something else is trustworthy.

First · days
D-01, D-02, D-03. One repo, end to end: CLAUDE.md, a verification command, hooks in managed settings. Small enough to finish inside a sprint, and it is what makes E-04 and E-20 safe to turn on.
Alongside
Existing Phase 01 ENG and LEAD work, unchanged. E-00, E-01, E-02, E-20, L-01, L-02, L-11 are all correctly placed and independently valuable. L-01 picks up the gate-depth extension.
Then
D-04, D-05, D-09. Encode the policies, wire intent capture into the repos, stand up the eval suite. D-09 before E-11's CI gates go live, so the gates are measured rather than assumed.
Then
D-10, D-06, D-07, D-11. AI review is the item most directly aimed at your stated target of days from Done to live — it removes the review queue rather than coordinating around it.
Last
D-08, D-12, D-13. Parallelism only after review capacity is real; rollback drills and telemetry alongside E-13 and L-05.

What v4 has that the playbook does not

The course is written for a generic enterprise. Several parts of your plan have no counterpart in it and should not be diluted.

E-00 Release Engineer orchestrator. The course has no event-bus conductor; its stages are triggered by committed artifacts. Yours is a real improvement for a multi-tenant release.
The per-customer layer. E-03, E-06, E-21, E-22, E-23, L-06. The playbook stops at the deploy boundary and has nothing on customer impact, UAT that travels, or downtime expectations.
Three-tier release model and the Comm SLA matrix. L-01 and L-02 have no equivalent play and are what let the gate redesign above be safe.
The deprecation program. E-10, E-16, L-08 — a tracked runway with usage signal and a dedicated cleanup release. Nothing like it in the course.
SOC framing as a side effect of process. The playbook treats governance as constraint; v4 treats evidence as output. That is the better framing — it just needs Git and hooks doing the work.
Documentation agents. E-18 and E-19. The course never addresses technical docs or customer how-to guides at all.
